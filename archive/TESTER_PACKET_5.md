## Что нового относительно v3 (одна фича, но большая)

В YAML-шаге появился `bind:` — привязка входов, которая **перекрывает `from:` из манифеста** для этого конкретного вызова:

```yaml
- id: refine
  plugin: plugins/text_analyzer   # тот же плагин, что вызывался шагом раньше
  bind:
    text: steps.review.text       # вместо from по умолчанию — текст с гейта
```

Следствия:

1. **Один плагин — сколько угодно раз в цепочке** с разной разводкой. Это и был блокирующий сценарий.
2. `from:` в манифесте стал **необязательным** — можно писать плагины «без привязки», разводку обязан дать пайплайн. Полезно для плагинов-«утилит» вроде вашего text_analyzer.
3. Валидация **до запуска** ловит: опечатки в именах портов bind (перечислит существующие), отсутствие привязки вообще, несовместимость типов/форматов через bind, чтение из skip-able шага без `optional` — всё то же, что с `from`.
4. Обратная совместимость: ваши пайплайны `format_version: "0.1"` работают без изменений.

Полные правила — `PROTOCOL.md`, §9.

## Самопроверка (5 минут, ключи не нужны)

```bash
./tool validate pipelines/llm_same_provider.yaml
LLM_MOCK=1 ./tool run pipelines/llm_same_provider.yaml
```

Это наш референс-сценарий: **один провайдер LLM дважды** — черновик → гейт с правкой →
доработка правки тем же плагином. В гейте замените текст на свой и убедитесь, что
второй вызов получил именно его.

## Главное задание (≈20–30 минут)

**Соберите СВОЮ цепочку, в которой один плагин вызывается дважды через `bind`.**

Берите свой код и свою задачу — важен не наш пример, а ваш путь. На выбор:

- **A (рекомендую, ближе к вашему плагину):** `text_analyzer` дважды — посчитать метрики
  черновика, человек правит текст на гейте, тот же text_analyzer считает метрики
  итогового текста. Сравнение «до/после» — реальный паттерн?
- **B:** свой новый плагин «без привязки» (манифест без `from`) + пайплайн, который
  зовёт его дважды с разными входами. Заодно проверим сценарий «утилита для каталога».
- **C:** любой ваш вариант — свобода важнее шаблона.
