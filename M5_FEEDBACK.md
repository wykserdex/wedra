## Пакет от тестера №3, круг 2 (28.08) — семантическая дыра format

Тот же OSINT-плагин (нормализация результатов Maigret-чекера) прогнан по полному
циклу на v7: plugin validate ✓ → plugin test 2/2 ✓ → pipeline validate ✓ → run ok=1.
Но по дороге он поймал **наш** дефект, не свой:

```yaml
input:
  results: { type: array, format: json }     # авторская интуиция
```
→ `plugin validate` проглатывал (форматы в манифесте не проверялись вообще),
а взрыв прилетал на pipeline validate чужим языком:
«формат источника "" не покрывает требуемый "json"». Его оценка: WTF-момент.
(Причина, если копнуть: "json" нет в formatRank, а format — подтип строк;
на array он семантически бессмыслен.)

→ ✅ **исправлено в v8**: `plugin validate` теперь отклоняет (1) `format` на
  не-string портах — с объяснением «для array уберите format: форму покроет
  type, состав элементов проверяйте внутри плагина»; (2) неизвестный format —
  со списком допустимых. Проверка на input И output портах. PROTOCOL §4
  дописан. 93 теста зелёные. Его дословный кейс воспроизводится: ругается на
  месте, после удаления format — OK.
  Изначальный его вывод (круг 1) сохраняется: как только сообщения стали
  локальными и точными — он же это и похвалил. Теперь они локальны и здесь.

Следствие в бэклог (НЕ делать до повтора): `--example array` мог бы содержать
в шаблоне закомментированный WRONG-блок `format: json` с зачёркнутым комментом
«так делал тестер №3 — валидатор отклонит»... но это уже украшательство.

**Баги (критичные, воспроизводимы на репе):**

### №9 — human_gate молча теряет данные при совпадении basename — критично
`gate.go:35` basename(f.Field). Два поля steps.before.file_count и steps.after.file_count → второй затирает первый без предупреждения. Воспроизводится на нашем собственном демо dir_snapshots.yaml: контекст показывает только after. Downstream, читающий steps.review.file_count по §7, получит after вместо before и не узнает. Плюс edits — map, порядок nondeterministic.
→ **Исправлено в v9**: gateMaterialize теперь считает коллизии basename; при коллизии ключ = <step_id>_<basename> (before_file_count, after_file_count) — данные сохраняются. validate.go теперь предупреждает: «базовое имя file_count встречается в [steps.before.file_count steps.after.file_count] — будут ключи вида <step_id>_file_count». dir_snapshots.yaml теперь проходит с warning и материализует оба значения. Тест dir_snapshots: before_file_count=3, after_file_count=4 оба в контексте.

### №10 — optional-порт без привязки = жёсткая ошибка, ломает смысл v0.2
`validate.go:194` кидает «нет привязки» ДО проверки port.Optional, хотя ниже для optional-привязанного в никуда даёт warning «optional — допустимо». Инверсия: не привязать optional нельзя, а привязать к несуществующему — можно. PROTOCOL §9.5 обещает «манифест без from легален — привязку обязан дать пайплайн» — но для optional пайплайн обязан дать привязку, которая не нужна.
→ **Исправлено в v9**: если port.Optional && srcPath=="" → warning, не error. Проверка: pipeline с optional-портами без bind теперь OK с warning.

### №11 — на exit>=2 конверт плагина выбрасывается, error.code всегда crash
`executor.go:161` ветка default ставит crash, а настоящий конверт запихивается в ErrMsg строкой. Плагин вернул {"code":"bad_input","message":"path должен быть строкой"} + exit 2, а тест сказал «ожидали bad_input, получили crash (exit 2: {...})». Невозможно различить «битый вход» vs «assert упал». Генератор сам учит печатать конверт с code:bad_input на битый JSON; README приводит expect exit_code 2 рядом с error.code no_api_key — читается что код на exit 2 утверждаем.
→ **Исправлено в v9**: парсим конверт и на exit>=2 — ErrCode = "platform:" + code (fallback crash), Platform остаётся true (ран стопится), но триаж возможен. plugin test теперь может ожидать platform:bad_input. Проверено на /tmp/crash_plugin.
