## Текст страницы

### Заголовок

> **Конвейер из плагинов: каждый кусок можно независимо написать, протестировать и заменить**

CLI-платформа, где многошаговая задача — это цепочка маленьких проверяемых плагинов
с гейтами человека между ними. Ввод → модуль → анализ → вывод — ровно в той форме,
какая нужна вам.

### Проблема

- Автоматизация вырождается в скрипты-однодневки: написали, запустили, забыли — трогать страшно.
- Когда «на тебя работает модуль анализа», на выходе — куча мусора, которую всё равно
  перебираешь руками.
- Связать три сервиса в цепочку — это клей-код на неделю, который никто не тестирует.

### Решение

Задача описывается одним YAML-файлом — цепочкой шагов. Каждый шаг — плагин с объявленным
контрактом: что читает, что возвращает, каких типов. Платформа проверяет совместимость
цепочки **до запуска**, а между шагами вы ставите гейты — человек смотрит, правит,
принимает или отклоняет.

```yaml
steps:
  - id: draft
    plugin: plugins/llm_gemini            # черновик
  - id: review
    plugin: core/human_gate               # человек правит текст
    form: [{ field: steps.draft.text, editable: true }]
  - id: refine
    plugin: plugins/llm_gemini            # тот же плагин, другая роль
    bind: { prompt: steps.review.text, system: input.refine_system }
```

### Три гарантии контракта

1. **Независимость.** Плагин не знает, откуда пришли его данные — он видит только свой
   вход. Поэтому его можно тестировать в одиночку (`tool plugin test`) и переставлять
   в любую цепочку.
   > «Плагин остаётся обычным Python-скриптом. Мне не пришлось писать SDK,
   > наследоваться от класса или импортировать внутренности оркестратора»
   > (тестер №3, после плагина корреляции идентификаций из нескольких источников).
2. **Проверяемость.** Типы и форматы объявлены в манифесте; несовпадения ловятся
   статической валидацией до запуска и контракт-тестами разработчика — вы не узнаёте
   о кривом плагине в середине рана.
   > «Ошибки не вылезают где-нибудь глубоко внутри Python — оркестратор говорит
   > буквально, какой порт и почему несовместим» (тестер №3, пойман валидатором
   > на своей же опечатке object vs array).
3. **Человек в узких местах.** `human_gate` — первоклассная ступень: посмотреть,
   поправить, принять или остановить. Никакого мусора «модуль посчитал — разбирайся сам».

### Один плагин — хоть десять раз

Разводка входов (`bind:`) живёт в пайплайне, а не в плагине. Один и тот же плагин
вызывается в цепочке сколько угодно раз с разными входами: черновик и доработка,
метрики «до» и «после», два источника — один инструмент.

### Класс задач — голосом пользователя

Первый внешний автор описал, для чего пользуется, лучше нас (пакет №5, почти дословно):

> «"До/после"-сравнение одним и тем же инструментом — снапшот состояния (файлы, метрики
> текста, конфиги) в двух точках времени с ручной сверкой на гейте между ними. У меня это
> конкретно: аудит директории до/после операции, где не хочется писать два почти
> одинаковых плагина ради одной и той же логики с разным входом».

### Для кого

- Автоматизаторы, у которых задачи — это **цепочки из разнородных шагов** (свои скрипты,
  чужие API, LLM, проверки), где важно заменять и чинить ступени по одной.
- Те, кто хочет конвейер под свою форму работы, а не под чужую.

### Честно о статусе

MVP: только терминал и YAML, GUI нет (осознанно — ценность в контракте).
Windows / Linux / macOS, один бинарник.

### Призыв

**Ищем 2–3 тестеров.** ZIP на вашу платформу, 15 минут до первого результата,
дальше — плагин под вашу задачу за вечер. Фидбек любой резкости приветствуется:
так уже исправлены баг матчера, типы выхода и добавлен контракт v0.2.

## Внутренний раздел: план набора (не для страницы)

**Гейт старта: СНЯТ** (пакет №5 подтвердил bind; далее пакеты №2/№3 дали 3/3
воронку и оценку ядра ~9/10). Реальные ресурсы автора: без бюджета и связей —
каналы сужены до **dev-чатов + репо**; тексты постов и чек-лист заливки —
`POSTS.md`. Эта страница (LANDING.md) больше не нужна как отдельный сайт:
её копирайт и цитаты переехали в шапку README (репа и есть лендинг).

**Профили тестеров (по 1 шт — ВСЕ ЗАКРЫТЫ: №1, №2, №3):**
1. Python-автоматизатор из личной сети — проверит порог входа и `plugin create/test`.
2. Человек с рутинной многошаговой цепочкой (аналитика/исследования) — проверит,
   ложится ли «ввод → модуль → анализ → вывод» на его задачу без переделки под демо.
3. OSINT-практик — **только как частный случай**: позиционирование остаётся
   универсальным, OSINT — демо-пак.

**Каналы по очереди:** личная сеть → тематические чаты → GitHub с этим лендингом.
Новые каналы не открываем, пока воронка текущего не отработана.

**Воронка и её замер (заполнять в M5_FEEDBACK.md):**
получил zip → запустил демо → собрал свою цепочку → написал свой плагин →
вернул фидбек. Каждое падение этапа = строка в журнале со словами тестера.

**Правило цикла (действует, подтверждено трижды):**
один пакет фидбека → разбор → **не больше одной фичи** в ядро → новый zip.
Бэклог (`--resume`, референс-манифесты v0.2 без `from`) остаётся замороженным,
пока его не попросит фидбек.
